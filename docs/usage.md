## 先确定要用哪份图

在 `D:/Agent/MyCode/web2kg` 的 `dev` 分支工作，保留 `main` 分支。先定义项目 Python，后续命令都使用它：

```powershell
$py = 'D:/Agent/MyCode/web2kg/.venv-research/Scripts/python.exe'
```

有三种容易混淆的图：

- **默认发布图**：由 `runs/active-graph.json` 指定，仍是旧 408 节点图。总控未传 `--graph` 时使用它。
- **独立实验的初始图**：实验开始时复制的输入，例如近期使用的 225 节点全索引图。它应保持不变，方便重现。
- **任务交接图**：一题执行及维护后的 `execution-graph`。只有完整、核验通过的交接才能作为后续输入；失败题的部分图不能直接替代它。

图目录和任务副本的用途见[资产说明](assets.md)。

## 查看图谱与人工核验

```powershell
# 默认发布图
& $py scripts/start_control.py

# 显式查看225节点全索引副本；端口可换
$graph = 'runs/reddit-complete-index-20261104-v1/reddit-jev-flash-expand225-20261104-v2/graph'
& $py scripts/start_control.py --graph $graph --port 8786 --manual-port 8785
```

服务启动后才可访问对应地址。第二条命令的总控是 `http://127.0.0.1:8786`。也可以双击项目根目录的 `start_console.cmd`。

打开总控不会启动 LLM 建图或正式任务。人工核验需在界面中启动：等待身份匹配的 Jina 服务，输入页面描述，查看候选截图，再选择目标检查真实路径回放。核验结果与正式任务评分分别记录。

若端口被占用，改用空闲端口。不要为了打开总控而关闭已有核验窗口、共用 Jina 或用户浏览器。

## 模型配置：不要把最近实验当作所有脚本的默认值

| 入口或用途 | 当前行为 |
|---|---|
| 最近独立建图 | Jev 排名与首次探索判断，可选 Jev 局部等价；Flash 生成描述、卡片、框架 |
| 最近 225 节点 Hard 实验 | Actor、selector、描述、卡片、框架、诊断和学习均为 Qwen3.7-flash，百炼直连 |
| `scripts/run_template_agent.py` | Actor 默认 `gpt-5.6-terra`，描述/卡片指定 `gpt-6-luna`，诊断默认 `gpt-6.1-sol` |
| `web2kg crawl` 通用 CLI | 探索方式默认 `grouped`；显式 `llm_ranked` 后才使用对应模型排名流程，Jev 需另选 provider |

`run_template_agent.py --model` 只改 Actor 模型，不能同时修改其他角色或切换到百炼协议。历史登记脚本也常绑定某次任务和资产来源，不是通用的新实验向导。

新运行应明确记录所有角色、模型、provider、预算、代理和输入来源。实际响应日志中的模型/供应商用于事后核对；密钥和登录态不放进公开报告。

## 建图入口与步骤

先查看参数，不会调用模型：

```powershell
& $py -m web2kg crawl --help
& $py scripts/build_qwen_graph.py --help
& $py scripts/register_graph_expansion.py --help
```

近期 Jev/Flash 图使用独立登记目录运行，流程如下：

1. 确定全新建图还是扩展已有图，选择独立输出目录。扩展时复制输入和已完成尝试记录，不直接改原图。
2. 登记状态数、深度、候选数、尝试数和模型调用上限，核对全部模型角色、站点副本与 Jina 身份。
3. 固定代码和输入，再由登记的入口执行。不要用开发源码替换已经开始运行的冻结文件。
4. 探索结束后，首次执行平均链接聚类、全量制卡和网站框架生成，再完成本地截图索引。
5. 核验图、描述、卡片、框架和索引是否完整，分别报告探索成本与知识层维护成本。

并行建图由浏览器线程连续探索，后台补描述并预取子页面候选排名。Jev 可通过明确的本地代理工作；Qwen 近期配置仍直连。相关凭据和网络说明见[环境](environment.md)。

`register_jev_graph.py`、`register_equivalence_rebuild.py`、`register_graph_expansion.py` 保存了具体开发实验的登记逻辑。使用前检查其继承的计划和硬编码来源，不能仅换输出目录就假定它适合另一网站或另一轮任务。

## 执行任务与正式评测

```powershell
& $py scripts/run_template_agent.py --help
& $py scripts/run_reddit_hard10_225.py --help
```

通用模板执行入口接收图目录、任务文本和新的 `--out`，支持独立登录态、起始 URL、是否允许写入及诊断参数。普通 CLI 不提供独立官方评分，因此不能仅根据 Agent 的 stop 文本学习成功经验。

当前开发版在 `execution-config.json` 中记录 `input_policy: task-memory-history-v1`。Actor 看到独立的任务记忆区、最近五步详细历史和更早的动作账本；旧步骤不会被整段删除，重复内容通过 `*_same_as_step` 引用前文。唯一的观察、选中证据、理由、输入内容与失败信息继续保留。调整示例配置的 `interaction_history.step_num` 只改变详细区的步数，不会删除更早的动作；设为 `all` 保留全部详细步骤。

输入中网站框架只展示概览和区域目录，当前卡片解释本页，邻近入口按目标合并。原始图谱、卡片、框架、模型响应和轨迹仍完整保存。压缩无需新的模型调用，未改变当前 AX、截图、单动作校验或诊断流程；旧冻结实验不能直接换用这版代码续跑。

近期正式 Hard 实验由登记器写入 `protocol.json`、输入清单和冻结源码，再由对应 runner 执行。任务 ID、初始图和经验、官方评分接口及允许重置的容器都在协议中固定。旧 runner 的报告或只读操作不能被误作重新启动任务的授权。

运行前检查 OS 队列和 worker 及其父进程，避免重复启动。运行中只读监测，不改配置、冻结输入或守卫。工程/永久服务错误停止并保留原评分；修复重跑使用新目录和明确的来源记录，不把旧失败覆盖为成功。

## 最近协议的主要参数

下表是已完成的近期 Flash 执行协议的值，不是每个旧脚本的默认值；当前开发版的行动额度调整见表后说明。

| 参数 | 最近设置及含义 |
|---|---|
| Actor + selector | 共 31 次逻辑调用；Actor 最多 30 个行动轮次 |
| 输出预算 | 登记值为每角色 4096；实际 token 以响应记录为准 |
| 描述、卡片 | 默认不设次数上限，所有物理调用继续计账 |
| 诊断与学习 | 共 5 次，最多 3 次诊断，一次返回最多 12 个回放动作 |
| AX 搜索 | 初始 800 行，窗口 800 行，最多 3 次，合并最多 2500 行 |
| 图容量 | 最新剩余31题设225；已完成的60节点Hard10单列；通用执行默认500，0关闭清退 |
| 闲置衰减 | 按检索轮次，默认 20 轮半衰期 |
| 全局聚类 | 平均链接，轮廓分容差 0.05 |
| 全局更新触发 | 至少 5 个变化模板，且占上次基准的 20% |
| 单卡更新触发 | 累计新增 + 删除成员严格超过 7，或超过上次人数的 75% |
| 独立框架刷新 | 最近协议设为 0；全局重整仍会生成框架 |

“31 次逻辑调用”不能当成全部物理请求上限。描述、制卡、诊断和重试都可能增加实际请求；返回成功返还的也只有行动步数，不返还模型调用。

2026-11-11起，本方法执行入口启用 `actor-action-v1`：`--max-calls` 限制 Actor 行动决策请求，`--max-steps` 仍限制行动轮次（包括 stop）。有效 AX 搜索和页面选择器不扣行动决策额度；同次格式重生成、传输重试共用一个决策编号。每轮最多三次 AX 搜索，搜索不可用时仍输出搜索会进入已有的有限纠错流程。辅助请求的物理次数、token、未知用量和等待时间全部保留，因此新规则允许的实际计算量可能多于旧协议。`execution-config.json` 记录计数策略，`result.json` 的 `action_budget` 分列额度使用量、AX 搜索和页面选择次数。原版 WebNavigator、AgentOccam 和历史冻结运行不采用此调整；新实验必须注明预算口径变化，不能直接当作旧版等计算量对照。

## 后台描述和收尾

动作后先保存事实与快照，描述作业在后台执行，Actor 不必每步等它。路线真正依赖这条边、诊断需要相关描述、队列满或任务结束时才等待。**未完成解释的新执行边不能直接回放。**

任务结束后先收齐描述，再裁剪图谱。随后可以并行补索引与生成卡片；收尾制卡最多三路，框架在全部卡片完成后生成。单卡小更新与全局聚类规则见[模板说明](../templates.md)。

`--no-graph-update` 关闭通用入口的执行增图；`--no-finalize-assets` 跳过资产收尾，也不会进行该阶段的裁剪。关闭增图时还需符合诊断入口的配置约束，不能假设恢复功能仍然可用。

## 诊断怎样使用，怎样判断有没有帮助

诊断可在无控件、反复到达同状态或连续无变化动作后触发。结论分三级：`on_track` 表示路径正确，继续执行；`uncertain` 表示怀疑偏离但证据不足，只给核验建议；`deviated` 表示明确偏离，才选择根因步骤、尝试返回并禁用原控件。前两级不回溯、不禁用控件、不消耗返回机会或返还步数。最新判断和建议进入后续 Actor 上下文，新的诊断替换旧建议，诊断总次数上限保持不变。

登记协议可额外传入 `direction_confidence`。默认 `mode: off`，不改变原有四栏输出；`shadow` 增加路线自评并记录哪些条件本会触发，`active` 才据此在动作前请求诊断。新代码中，只要诊断本身启用，连续十次实际 Actor 行动未诊断也会检查一次（置信度关闭时仍保留），搜索、格式重生成和自动回放不累计，三次诊断与一次返回的总额不增加。分数缺失记为未知，不按零分处理。诊断后清空短窗口，并给三个实际行动的置信度冷却期。暂定的 0.30／0.60 条件是待校准参数，不是已经验证的错误概率。分数及未执行提案保存在 `direction_confidence` 事件中，只有执行后的 `direction_confidence_committed` 事件计入行动链。

`shadow` 也可单独用于无诊断实验：不配置诊断客户端时仍记录分数和实际行动，但不触发诊断、十步检查或回溯。`active` 则必须配置诊断客户端。

实验运行器使用 `diagnosis_calls: 0` 关闭诊断及评分后的诊断经验学习，不创建零额度学习客户端。普通图谱维护与知识交接照常执行；官方评分已经保存但收尾失败时，仍保留为待处理尝试，不能直接重启或改写为完成。

`scripts/run_confidence_calibration.py` 登记独立失败案例采样：使用保留的初始图副本，每题清空任务经验，不继承上一题的新图。它不恢复旧全量队列，也不自动把试算阈值写回正式默认值。运行范围和检查凭据必须在新目录登记后，才使用该目录的冻结入口启动。

提示词要求区分“尚未核验”与“已证明错误”：例如没有显式切换排序，不足以证明默认排序不对；返回列表继续检查不同详情也可能是正常进展。三级分流约束程序如何处理结论，不能保证模型总能正确判断证据强弱。

自动返回优先走当前位置到目标的记录路径；无路或超过动作上限时，可以回到逻辑首页再走。回首页计一个动作，到达后按实际页面重新求路，整个返回仍受原有动作上限约束。诊断输入的每步页面摘要旁附 Actor 观察摘要，动作旁附该次 Transition 的 effect；不附 highlight。解释尚未完成时显示 pending，失败或未请求时注明状态，不把缺少解释当作动作失败。只等待所需页面摘要或可行返回路线依赖的 Transition，不为补齐 effect 等待全部后台解释完成。输入边、禁用控件和现场状态检查继续生效；实际回放失败后不换路重试。

返回失败也用掉本题唯一返回机会；目标状态核验成功才返还行动步数。查看 `recovery/report.html` 时，应分别判断：诊断是否触发、建议是否被采用、是否真实返回、最终是否通过外部评分。不要把它们合成一个“恢复成功”。

只有外部成功、返回成功且执行过替代操作，才会写成功经验。

## 重试、暂停和完整性检查

原版WebNavigator的Flash对照可在新协议中显式设置`section_parser: anchored-heading-v1`。它仅修复栏目识别：要求标题出现在行首，将`REASON FOR ACTION:`作为`REASON:`的别名，并支持全角冒号。未设置时保留原版解析，旧冻结实验不变；这不引入本方法的单动作提示词，也不改变模型输出截断时停止的处理。

2026-11-10起，开发目录的原版`stop.txt`采用`verified-json-stop-v1`：保留原回复栏目和`stop [answer]`命令，只将括号内答案统一为Verified JSON。`task_type`与`status`必填；检索数据放在`retrieved_data`数组中，`error_details`按结果填写。新Hard42登记会把此文件从冻结开发源复制进新批次的upstream，记录原、新哈希，并启用`unified_verified_stop`，不再叠加旧的自然语言回答说明。此次只适配提示词，没有增加原版的格式重试或改变导航逻辑；能否改善模型实际输出仍需新实验验证。旧冻结版本不变，提示词版本不一致时不能用`--continue-from`混合结果。

用户明确要求单题错误后继续时，`run_webnavigator_flash_hard.py`可在新目录登记`--continue-from`，引用上轮已结束的原始结果，只运行未开始题。新协议的`continue_task_errors`让worker异常保留为失败、尝试官方评分，再进入下一题；不自动重跑失败题、不补写答案。用户STOP仍停止整个队列，共享输入核验、编码器或环境重置失败也不能绕过。

AgentOccam 对照使用 `scripts/run_agentoccam_flash_hard.py`，在新目录登记后从该目录的冻结入口运行。模型为百炼 Qwen3.7-flash，保留原生 Agent、页面裁剪、历史和动作处理，没有图谱、Jina、卡片或本方法的诊断。stop 答案使用相同的 Verified JSON 合同，具体适配与原生语法限制见[实现说明](architecture.md#agentoccam-对照)。

最近本方法的 Flash 协议区分三类情况：临时传输错误按相同输入等待重试；成功响应但格式不合法时最多三次格式重生成；浏览器动作不会因上述重试再次执行。永久认证、余额、内容审核或工程错误不按临时连接错误处理。原版对照与旧协议沿用自己登记的规则，AgentOccam 的原生格式重生成仍消耗逻辑调用额度。

新开发版 Actor 使用 `compact-context-v1` 输出四个栏目：`OBSERVATION DESCRIPTION`、`REASON`、`ACTION`、`OBSERVATION HIGHLIGHT`，另可附 `NOTE`。高亮通常 1–3 个、最多 5 个，按重要性排序；程序去掉当前观察中不存在和重复的编号，再截取前 5 个，不增加模型请求。目标复述、约束列表、历史总结和模式分析不再要求输出。观察摘要和有效高亮继续用于历史上下文。

单动作检查仍使用 `single-action-v2`：多个动作会被整份拒绝，不挑第一个动作执行。纠错后在同一份观察下重生成，不扣行动步数，所有请求成本继续记录。通用 `run_template_agent.py` 可用 `--max-output-retries 0..3` 设置上限，默认3；正式实验使用登记值。重生成达到上限仍失败时停止，不无限循环。

最新纠错使用 `previous-response-v1`：请求附带上一次不合格的可见响应和具体错误，而不只追加通用提醒。原任务、观察、截图和控件编号不变；临时反馈只保留最近一次，进入下一轮动作后清除。重复相同动作仍需重新生成合法单动作，不自动执行或去重。

本方法的 `optimal_navigate` 第二个参数使用当前 Actor 已注册的站点名（例如 `reddit`），不是网址或主机名。提示词会列出实际可用名称；填错时，`registered-site-feedback-v1` 在导航前把错误值、允许的名称和原响应反馈给模型，在同一观察下纠正。至多收到三次非法站点响应，同时受原有最多三次输出重生成的共同上限约束，不额外叠加一轮重试。被拒响应不执行动作、不新增逻辑决策，物理请求和成本仍计入；原版对照保留原行为。

制卡的 `validated-card-v1` 将 JSON Schema 和业务校验放在同一个有限纠错流程内。每个功能变体需要1至5个实际代表页证据编号；没有证据支持时不写该变体，整个 `variants` 可以为空。纠错附上最新失败卡片、具体字段错误和原证据，最多三次重生成，不自动补编号或删改模型输出。截图变化、程序异常、永久服务错误不因此重试。旧冻结版本仍保留原行为。

225节点的新增31题登记了 `retain_score_keep_previous_handoff`：只有确认恰好耗尽Actor/selector逻辑调用额度，且没有其他服务、描述或资产错误时，才将本题记为 `budget_exhausted`，保留官方评分并进入下一道未开始题。原结果与未完成图不改写，也不交接；下一题使用最近完整图。该策略不增加调用额度，旧冻结队列仍按旧规则停止。

需要暂停时使用当前运行的停止机制，保留 STOP 和已完成证据，确认队列、worker 及独占服务退出。再次继续应检查未完成阶段；不要删除 STOP 后直接重启已经开始的任务。部分图和完整交接图必须区分。

`boundary-v1` 在版本开始和结束检查完整保护集合，每题检查当前输入、冻结源码和最新交接，并核对范围清单自身。它减少重复扫描，不依赖文件修改时间代替内容核验。图索引的编码器身份检查仍然保留。

报告应分别列出任务、收尾、编码器准备、环境重置、登记和完整性核验时间。并行请求时，各请求时长相加会大于墙钟时间，不能混为“一个 case 耗时”。
